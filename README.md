# Reflection

### What are the key differences between unary, server streaming, and bi-directional streaming RPC (Remote Procedure Call) methods, and in what scenarios would each be most suitable?
Unary is the basic request-response pattern. You send one request and get one response, just like a typical HTTP call. This works well for simple tasks such as fetching a user profile or submitting a payment. With server streaming, you send a single request, but the server keeps the connection open and sends back multiple pieces of data over time. This is helpful for downloading large files or receiving live updates, like match scores. Bi-directional streaming lets both the client and server keep the connection open and send messages to each other whenever needed. This is ideal for real-time apps, such as chat services or live multiplayer games.

### What are the potential security considerations involved in implementing a gRPC service in Rust, particularly regarding authentication, authorization, and data encryption?
By default, gRPC does not encrypt data if it runs over plain HTTP/2. For production use, you need to set up TLS to keep data secure during transmission. Since gRPC does not use browser cookies for authentication, you have to use interceptors. This involves sending something like a JWT (JSON Web Token) in the request metadata, and the server must check and validate the token before handling the RPC call.

### What are the potential challenges or issues that may arise when handling bidirectional streaming in Rust gRPC, especially in scenarios like chat applications?
The hardest part is managing concurrency and state. Since messages go both ways at once, you need to handle asynchronous tasks without blocking the main thread. In Rust, this often means using tokio channels and Arc/Mutex to share state, such as a list of active chat rooms, across connections. You also need to handle disconnects smoothly. If a client loses connection, the server should clean up the stream and channel properly to avoid errors.

### What are the advantages and disadvantages of using the tokio_stream::wrappers::ReceiverStream for streaming responses in Rust gRPC services?
The main benefit is convenience. It connects tokio’s mpsc channels with the stream types that Tonic expects for client responses. You can pass the receiver end of a channel into the wrapper, and it manages stream polling automatically. The downside is some added structural overhead. You also need to watch the channel buffer size. If the client reads slower than the server sends, the buffer can fill up and pause the server’s sending task.

### In what ways could the Rust gRPC code be structured to facilitate code reuse and modularity, promoting maintainability and extensibility over time?
Currently, most of the code is packed into just a few files, which makes it hard to maintain. To improve this, I would organize the project into clear layers. The generated protobuf code would go in its own module, while business logic like database operations or payment calculations would be in separate core modules. The gRPC service code would only handle transport. This setup makes it easier to add a REST API gateway or change the database later without rewriting the main logic.

### What impact does the adoption of gRPC as a communication protocol have on the overall architecture and design of distributed systems, particularly in terms of interoperability with other technologies and platforms?
Using strict .proto contracts makes teams more disciplined. Frontend and backend developers cannot create random JSON structures, which helps prevent errors. Interoperability is much easier because you can write the backend in Rust and the frontend in Flutter, and both use the same data models from the .proto file. The downside is that debugging is harder since the data is in binary, so you cannot easily read the network payload in plain text.

### What are the advantages and disadvantages of using HTTP/2, the underlying protocol for gRPC, compared to HTTP/1.1 or HTTP/1.1 with WebSocket for REST APIs?
HTTP/2 is faster because it can handle multiple requests over one TCP connection and compresses headers, which reduces latency. It also supports server push by default. However, HTTP/2 is more difficult to debug and proxy. Many older load balancers and network tools only support HTTP/1.1, so setting up the right infrastructure for gRPC traffic can be more challenging.

### How does the request-response model of REST APIs contrast with the bidirectional streaming capabilities of gRPC in terms of real-time communication and responsiveness?
With REST, building real-time features usually means constantly polling the server for new data, which is inefficient, or switching to WebSockets. gRPC supports real-time communication with streaming by keeping the HTTP/2 connection open, allowing the client and server to send data whenever needed. This approach is more responsive and has less overhead because you do not have to repeatedly open and close connections.

### What are the implications of the schema-based approach of gRPC, using Protocol Buffers, compared to the more flexible, schema-less nature of JSON in REST API payloads?
Protocol Buffers are amazing for performance and type safety. Because the schema is compiled, the payProtocol Buffers offer great performance and type safety. Since the schema is compiled, payloads are serialized into a compact binary format, making them smaller and faster to send than JSON. You also catch type errors at compile time. However, JSON is more flexible and easier to read. With a REST API, you can use tools like Postman or a browser to see the response directly. With gRPC, you need special tools like grpcurl and must have the .proto file to understand the response.
